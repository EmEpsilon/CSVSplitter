# CSVSplitter 高速化レビュー（2026-04-28）

## 目的

現時点のコードを全体的に確認し、**即時実装はせず**、高速化余地のある箇所を候補として整理する。
本ドキュメントは「改修案 + リスク + 検証観点」をまとめた協議用メモ。

## 先に結論（優先度順）

1. **CSV行数カウントの事前パス削減（最優先）**
   - 変換前に全入力ファイルを `CountCsvFileAsync` で1回読み、さらにソート/出力で再度読むため、I/Oが増えている。
2. **外部マージ処理の `O(k)` 最小探索をヒープ化（高優先）**
   - `MergeCsvFileAsync` が毎レコードごとに全入力を線形走査して最小要素を決めている。
3. **大量行ソート時のオブジェクト割り当て削減（高優先）**
   - `SortCsvRow` が `IDictionary<string, object>` と `RawData` を持ち、行数増加時のGC負荷が高い。
4. **分割出力のルーティングキー構築コスト削減（中優先）**
   - 毎行 `List<string>` + `StringBuilder` でキーを生成しており、割り当てが多い。
5. **小～中規模ソート時の並列化戦略見直し（中優先）**
   - `AsParallel().OrderBy(...).ToList()` が常に有効で、データ量次第で逆効果。

## 観測したボトルネック候補

### 1) 事前カウントの追加I/O

- `Execute` で全入力に対し `CountCsvFileAsync` を実行し、総レコード数を出して進捗の母数に利用している。
- `CountCsvFileAsync` は `CsvReader.ReadAsync()` + `GetRecord<dynamic>()` を回すため、単なる行数取得以上にCPUを使う。

**影響**
- ファイルが大きいほど、変換本処理前にほぼ同量のI/Oが発生。
- SSDでも体感時間増、HDD/NASで顕著。

**改修案**
- A案: 事前カウントを廃止し、進捗を「フェーズ進捗（分析/ソート/出力）」に変更。
- B案: 事前カウントを維持する場合は `GetRecord<dynamic>()` を使わず、CSVパーサのread回数のみで数える。
- C案: 既存の分析フェーズ（Analyze）で行数を併せて採取し、変換時に再利用。

**リスク**
- A案: 進捗バーの意味が「件数比」から変わるため、UI期待値変更。
- C案: Analyzeボタン押下時の待ち時間が増える可能性。

---

### 2) マージ処理の計算量

- `MergeCsvFileAsync` は、各行出力時に `inputList` 全体を走査して最小行を探す。
- 分割ソートで一時ファイル数が増えると、総コストは概ね `O(N * k)`（N=総行数, k=入力本数）。

**改修案**
- `PriorityQueue<CCInput, SortKey>`（.NET標準ヒープ）または独自最小ヒープを使い、`O(N log k)` に変更。
- 比較器は既存 `SortComparer.CompareRecords` を流用。

**リスク**
- 並び順の安定性（同値時の順序）を要件化しないと、結果差分が出る場合がある。

---

### 3) ソート対象レコードのメモリ/GC

- 現在は `SortCsvRow` ごとに `Data`（辞書）と `RawData`（行文字列）を保持。
- chunk単位で多数行を保持するため、LOH/Gen2 GC を誘発しやすい。

**改修案**
- `Data` を保持せず、比較に必要な列のみを先に抽出した軽量構造体へ。
- `RawData` についても必要なら `ReadOnlyMemory<char>` など参照主体にする（実装可能範囲で）。
- 数値比較列は `double` への前変換を維持し、文字列比較列は `string` を最小限保持。

**リスク**
- CsvHelperのAPI依存を減らす改修は実装難度が高め。
- 引用符・改行含むセルなどCSV仕様境界で回帰が出やすい。

---

### 4) 分割出力のキー生成と文字列操作

- `OutputCsvFileAsync` で行ごとに `headerData` を `List<string>` に積み、`BuildSplitRoutingKey` で結合キーを生成。
- `GetOutputFilePath` でも毎回 invalid char 置換ループを回す。

**改修案**
- split列インデックスを先に確定し、`List<string>` を使わず固定長配列/ValueTuple化。
- キーは `ValueTuple` か専用 `struct` + `IEqualityComparer` にして文字列結合を減らす。
- ファイル名サニタイズはヘッダ値ごとにキャッシュし再利用。

**リスク**
- キー型変更で辞書の同値性実装を誤ると、分割ファイルが誤って統合/分離される。

---

### 5) 並列ソートのしきい値

- `count <= maxSortFileRecords` と chunkソートの双方で `AsParallel().OrderBy` を使っている。
- 中小データではPLINQの分割/マージコストが勝ち、遅くなる可能性。

**改修案**
- 行数しきい値（例: 2万件未満）では `List<T>.Sort(comp)` を使う。
- CPUコア数やUI応答性を考慮し、並列度を制限可能にする。

**リスク**
- データ分布や列数で最適値が変わる。固定しきい値は環境依存。

---

## 実装前にやるべき計測（推奨）

1. **ベースライン計測**
   - データサイズ: 10万 / 100万 / 500万行
   - パターン: 単一ファイル、複数ファイル統合、分割キー高/低カーディナリティ
2. **測る指標**
   - 総処理時間、フェーズ別時間（count/sort/merge/output）
   - Peak Working Set / GC回数（Gen0/1/2）
   - 一時ファイル数、マージ対象本数
3. **採用判断ライン**
   - まずは「総処理時間20%以上短縮」または「同時間でメモリ30%以上削減」を目標にする。

- 並列ソートしきい値導入
